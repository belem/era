## Feature Specifications

### Review Events Table (NEW — Critical Foundation)

**Problem:** `poem_reviews` uses `UPSERT ON CONFLICT (student_id, poem_id)`, overwriting
the previous rating on every review. Algorithm migration, streak computation, and session
summary all need the full review history. Without this table, those features are blocked.

**Schema note:** Supabase has no real user data. All schema changes (review_events,
new columns, badges, guardian_invitations) should be incorporated directly into
001_initial_schema.sql as clean CREATE statements, not as ALTER migrations. Cleaner,
fewer files, no migration chain to maintain. Re-seed poems after schema change.

**Schema** (add to 001_initial_schema.sql):
```sql
-- Append-only review event log. poem_reviews stays as current-state snapshot.
CREATE TABLE review_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  student_id UUID NOT NULL REFERENCES students ON DELETE CASCADE,
  poem_id UUID NOT NULL REFERENCES poems ON DELETE CASCADE,
  algorithm srs_algorithm NOT NULL,
  rating TEXT NOT NULL CHECK (rating IN ('forgot', 'hard', 'good', 'easy')),
  reviewed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_review_events_student_date
  ON review_events(student_id, reviewed_at);

-- RLS: same guardian pattern as poem_reviews
ALTER TABLE review_events ENABLE ROW LEVEL SECURITY;
CREATE POLICY review_events_select ON review_events FOR SELECT
  USING (EXISTS (SELECT 1 FROM student_guardians sg
    WHERE sg.student_id = review_events.student_id AND sg.guardian_id = auth.uid()));
CREATE POLICY review_events_insert ON review_events FOR INSERT
  WITH CHECK (EXISTS (SELECT 1 FROM student_guardians sg
    WHERE sg.student_id = review_events.student_id AND sg.guardian_id = auth.uid()));
```

**API change:** `/api/schedule` POST handler inserts into `review_events` (append)
AND upserts `poem_reviews` (current state snapshot). Two writes per rating, same
transaction. `poem_reviews` remains the fast lookup for "what's due next."

### Leitner + FSRS Algorithms

**Schema changes** (updated schema, on `poem_reviews`):
```sql
-- Use existing srs_algorithm ENUM from students table, not a new TEXT column.
-- The algorithm used for each poem is tracked per-event in review_events.algorithm.
-- poem_reviews stores current SRS state for the active algorithm only.
ALTER TABLE poem_reviews ADD COLUMN leitner_box INT DEFAULT 0;
ALTER TABLE poem_reviews ADD COLUMN fsrs_stability FLOAT;
ALTER TABLE poem_reviews ADD COLUMN fsrs_difficulty FLOAT;
ALTER TABLE poem_reviews ADD COLUMN fsrs_reps INT DEFAULT 0;
```

> **Note:** No `algorithm TEXT` column on `poem_reviews`. The student's active algorithm
> is already stored in `students.algorithm` (type `srs_algorithm` ENUM: 'SM2', 'LEITNER',
> 'FSRS'). Per-review algorithm is logged in `review_events.algorithm`. Adding a redundant
> TEXT column with different casing ('sm2' vs 'SM2') was a bug in the original spec.

**Algorithm factory** (`src/lib/srs/algorithm-factory.ts`):
- Strategy pattern: `getAlgorithm(name: 'SM2' | 'LEITNER' | 'FSRS')`
- Match the existing `srs_algorithm` ENUM values (uppercase)
- Each algorithm implements: `schedule(state, rating) => { nextReviewAt, updatedState }`
- SM-2: existing `src/lib/srs/sm2.ts`
- Leitner: new `src/lib/srs/leitner.ts` (~30 LOC, 5 boxes, fixed intervals)
- FSRS: new `src/lib/srs/fsrs.ts` (wraps `ts-fsrs` npm package)

**FSRS tier gating:** ~~Removed by eng review.~~ FSRS is available to all tiers. No lock
icon, no 403, no tier checking. The original design doc DD#4 had paid-tier gating, but
the eng review recommended unlocking it for all users to reduce complexity and improve
the algorithm comparison experience.

**Algorithm switching (all algorithms):** When guardian changes algorithm, the new
algorithm recalculates scheduling state from `review_events` (the append-only log).
Past ratings and dates are always preserved in `review_events`. This applies to all
transitions (SM2→FSRS, FSRS→LEITNER, etc.). Each algorithm implements
`migrateFromHistory(events: ReviewEvent[]) => state`.

**FSRS migration:** When guardian changes algorithm from SM2/LEITNER to FSRS:
- Runs server-side in `/api/schedule` route (not Edge Function, to avoid cold start)
- Reads full event history from `review_events` for the student
- Recalculates FSRS state using ts-fsrs formula
- Shows loading state in UI: "Recalculating schedule..." (typically <2s for 200 poems)
- On failure: rollback to previous algorithm, show error toast
- Estimate: 200 poems x 10 events = 2000 calculations, <1 second

### Configurable Session Size

Two settings in `students.settings_json`:
- `new_poems_per_day`: INT, default 3, range 1-20
- `max_reviews_per_session`: INT, default 15, range 5-50

**Review queue ordering:** `useReviewQueue` applies:
`FROM poem_reviews WHERE next_review_at <= now() ORDER BY next_review_at ASC LIMIT max_reviews_per_session`.
Uses `next_review_at` for ordering (exists on all algorithms), NOT `stability` (FSRS-only).

**New poem detection:** Poems the student hasn't reviewed yet are discovered by
anti-joining `poems` against `poem_reviews`:
`FROM poems WHERE id NOT IN (SELECT poem_id FROM poem_reviews WHERE student_id = ?) LIMIT new_poems_per_day`.
No `first_review` column needed. The absence of a `poem_reviews` row IS the "new" signal.

**Server-side enforcement:** `max_reviews_per_session` is client-side only (applied in
`useReviewQueue` query). A tech-savvy child could bypass via dev tools. Acceptable for
Phase 2; server-side rate limiting is a Phase 3 concern.

Parent sets these in student settings page.

### Streak Freeze

**Streaks use both `review_events` and the existing `streaks` table:**
- `review_events` is the source of truth for computing streak length
  (query: count consecutive days with >=1 event, backward from today)
- `streaks` table (already exists in 001_initial_schema.sql) caches the computed value
  for fast reads. Updated after each session, not computed on every page load.
- Index: `CREATE INDEX idx_review_events_student_date ON review_events(student_id, reviewed_at::date)`
  (already included in review_events schema above)

**Freeze settings** in `students.settings_json`: `streak_freeze_enabled: BOOL` (default true),
`streak_freeze_used_this_week: DATE | null`
- One automatic freeze per calendar week (Mon-Sun). No manual activation.
- When streak is computed and a gap day is found:
  if freeze available and not used this week, preserve streak, mark freeze as used.
  Otherwise, reset streak to 0.
- Free feature, all tiers. Aligns with "quiet gamification" (no anxiety).
- UI: streak counter shows a small snowflake icon on frozen days.

**Badge icon format:** Custom SVG icons, monochrome, consistent 2px stroke weight.

- Unlocked: `--badge-N` border color, `--text` fill, `--bg-subtle` background

unlocked badges (if any). Client stores result but does NOT show a popup or toast.

profile, like finding stamps in a passport.

and `badge_unlocks` table (student_id, badge_id, unlocked_at). Pre-seeded in migration.

### Guardian Invitation Flow

**Schema** (migration 003):
```sql
CREATE TABLE guardian_invitations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  student_id UUID REFERENCES students(id),
  invited_by UUID REFERENCES auth.users(id),
  invited_email TEXT NOT NULL,
  token UUID UNIQUE DEFAULT gen_random_uuid(),
  expires_at TIMESTAMPTZ NOT NULL DEFAULT (now() + interval '7 days'),
  accepted_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

**Email infrastructure:** Supabase's built-in email handles auth flows only (signup,
password reset). Custom transactional emails (invitations) require a separate provider.
Add `resend` npm package as dependency. Configure Resend API key in environment.
Alternative: Supabase Edge Function with SMTP, but Resend is simpler and has a free tier.

Sub-tasks:
1. **Generate invitation** — API route creates token (UUID), stores in `guardian_invitations`
   table (new migration), sets `expires_at` to 7 days from now
2. **Send email** — Resend SDK (`npm install resend`). Email contains accept link
   (`/invite/accept?token=xxx`). Requires `RESEND_API_KEY` env var.
3. **Accept page** — `/invite/accept` validates token, shows student name, "Accept" button
   links guardian to student via `student_guardians` table
4. **Family management** — Settings section showing linked guardians per student.
   Owner can remove non-owner guardians
5. **Edge cases:** expired token (show "Request a new invite" message), already linked
   (show "You're already connected to this student"), self-invite (prevent in API)

### Auth Error Visual Spec

All auth form errors use inline placement directly below the relevant field:
- Error text: 14px, system sans, `--error` color
- Field border: changes to `--error` color with 0.3s shake animation
- "Wrong password" → below password field, with "Forgot password?" link
- "Email not verified" → below email field, with "Resend verification" link (rate-limited 1/60s)
- "Account locked" → replaces submit button with "Too many attempts. Try again in X minutes."
- "Email not found" (forgot password) → below email field
- OAuth conflict → banner above form: "This email is registered with [provider]. Sign in with [provider] or link accounts."

### Guardian Invite Accept Page (`/invite/accept`)

**Route:** `/invite/accept?token=xxx`

**Flow for new users (no account):**
1. Page loads → validates token via API → shows invite preview
2. Preview: student avatar circle + student name + "invited by [guardian name]"
3. Below preview: "Create an account to accept" primary button
4. Button navigates to `/login?redirect=/invite/accept?token=xxx` (token preserved in URL)
5. After signup/login → redirect back to accept page → show "Accept invitation" button
6. Accept → success screen: "You are now linked to [student]! 🎉" + "Go to home" pill CTA

**States:**
- Loading: centered spinner + "Validating invitation..."
- Expired: "This invitation has expired." + "Ask [inviter name] to send a new one." (no retry button, inviter must resend)
- Already linked: "You're already connected to [student]." + "Go to home" pill CTA
- Self-invite: "You can't accept your own invitation." (API rejects, shouldn't normally reach this page)
- Not signed in: invite preview visible + "Create account to accept" CTA
- Success: confirmation with student name + "Go to home"

**Visual:** Centered card (max-w-sm), no AppHeader, no TabBar. Similar layout to login page. Student avatar uses same circular style as ProfileSwitcher (but larger, 64px).

### SVG Icon Convention (NEW — Design Spec)

**All icons in Phase 2 use custom SVG, not emoji.** This includes:
- Badge icons (scroll, flame, moon, star, seal) — `public/badges/`
- Algorithm metaphor icons (curve, boxes, brain) — `public/icons/`
- Streak flame and snowflake — `public/icons/`
- Tab bar icons (home, library, gallery, profile) — replace existing emoji in Phase 2
- Theme toggle (sun, moon) — replace existing emoji

**SVG style:** Monochrome, 2px stroke weight, `currentColor` fill/stroke for theme compatibility.
Default size: 20px inline, 24px standalone, 52px badges. Stored as individual `.svg` files
or as a React component library (`src/components/icons/`).

**Rationale:** Emoji renders differently across platforms (a fire on iOS vs Android vs Windows
looks completely different). SVG ensures visual consistency and works with the design system's
color tokens.
