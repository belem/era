## Problem Statement

Classical Chinese poetry memorization is a core part of primary and middle school education in China, but existing tools are either pure reference apps (browse/search) or gamified quiz apps with no scientific scheduling. Anki has spaced repetition but zero cultural aesthetics and is intimidating for parents and young children. There's a gap for a beautifully designed, parent-managed, scientifically-backed poetry memorization platform that respects the cultural weight of the material.

## What Makes This Cool

The intersection of three things no one is combining well:

1. **Apple-inspired minimalism + cultural punctuation** — The app draws from Apple's reductive design philosophy: controlled drama, cinematic spacing, and a singular accent color. Cultural identity comes through typography (思源屏显臻宋 Source Han Serif CN for Display, Noto Serif SC) and the Living Scroll interaction, not through surface decoration. The design should feel like a precision-crafted instrument, not a museum exhibit.

   **Color philosophy — Apple's controlled palette:** The color system is starkly binary, inspired by Apple's website. Surfaces alternate between pure white (#ffffff) and light gray (#f5f5f7) in light mode, and pure black (#000000) with dark surfaces (#1c1c1e) in dark mode. This creates cinematic pacing — dark sections feel immersive, light sections feel open. The singular interactive accent is Apple Blue (#003D74 light, #2997ff dark) — reserved exclusively for CTAs, links, focus rings, and active states. Every clickable element gets unmistakable visibility through this single hue. Text uses near-black (#1d1d1f) with secondary (#6e6e73) and tertiary (#86868b) grays for hierarchy. For content-level accents only (polyphonic character markers in poetry), a warm coral (#ff6b6b) is used — this is never applied to interactive UI elements. Semantic colors follow Apple's system: green (#34c759) for success/Easy, red (#ff3b30) for errors, orange (#ea5414) for warnings. Badge tiers use a minimal palette: orange → blue → green → near-black.

   **Typography — three voices, carefully paired:**

   The app speaks in three typographic registers. Each one is chosen for a reason that goes beyond "looks nice."

   **Voice 1 — Poetry body: 思源屏显臻宋 (Source Han Serif CN for Display)**, loaded from `chinese-fonts-cdn.konghayao.deno.net`. A high-quality Song-style typeface derived from Source Han Serif, optimised for on-screen display. Its structured strokes give poetry a refined, archival quality that pairs naturally with Noto Serif SC headings. Set `font-feature-settings: "kern" 1` and track letter-spacing at 0.05em for poetry lines to give each character room to breathe.

   **Voice 2 — Headings and structure: Noto Serif SC** (思源宋体), loaded from Google Fonts. Song/Ming style (宋体) carries the authority of printed books. It's what you see on the title page of a classical collection, the spine of a thread-bound volume (线装书). The vertical strokes are thin, the horizontal strokes have weight, and the serifs (顿笔) give each character a sense of being placed, not typed. Use SemiBold (600) for page titles and section headers, Regular (400) for secondary headings like dynasty/author labels. The contrast between Kai (handwritten warmth) for poetry and Song (printed authority) for structure creates a natural visual hierarchy without needing size differences alone. This pairing has centuries of precedent in Chinese book design, where the cover is Song and the interior is Kai.

   **Voice 3 — UI and pinyin: system sans-serif + Inter.** Buttons, navigation, labels, timestamps, and all functional text use the system's native sans-serif stack: `"PingFang SC", "Microsoft YaHei", "Noto Sans SC", system-ui, sans-serif`. This is intentionally invisible typography. It loads instantly (no web font download), it's what users read every day on their devices, and it signals "this is the app talking to you" as distinct from "this is the poetry." For pinyin annotations above characters and any Latin text (email addresses, URLs, version numbers), use Inter (Google Fonts) — its x-height and letter spacing are optimized for small sizes and it pairs cleanly with both 思源屏显臻宋 and Noto Serif. Pinyin renders at roughly 45% of the character's font size, in a lighter color (not the same ink-black as the character itself), sitting above like a teacher's pencil note — present when you need it, easy to ignore when you don't. The `heti--annotation` container handles interlinear grid alignment so `<ruby>/<rt>` stacks consistently without fighting browser defaults — every character gets equal vertical clearance regardless of whether its pinyin ascends (ā, á) or descends (à).

   **Font loading strategy:** 思源屏显臻宋 (Source Han Serif CN for Display) is loaded via CDN stylesheet from `chinese-fonts-cdn.konghayao.deno.net`. Add the `<link rel="stylesheet">` in `<head>`. Noto Serif SC is loaded from Google Fonts — preload with `<link rel="preload">` since it renders headings on first paint; its system fallback (`"Songti SC", "SimSun", serif`) is acceptable during swap but visually distinct enough to warrant preloading. Inter is tiny (~100KB variable).

   **Space — the art of leaving blank (留白):** Classical Chinese composition prizes negative space as much as the mark. A poem of twenty characters should feel like it's floating in open air, not crammed into a card. Generous margins. Vertical rhythm that lets each line breathe. The screen should never feel full. When in doubt, remove, don't add. This is the hardest design discipline and the one that will most distinguish Kuibu from every other education app.

   **Surfaces — clean, not textured:** No paper grain, no warm tinting, no skeuomorphic textures. Backgrounds are flat solid colors. Visual depth comes primarily from background-color contrast, not shadows or borders. Borders are used sparingly (neutral gray #d2d2d7 light / #38383a dark). Cards and sections are defined by background-color shifts between --bg (#ffffff / #000000), --bg-subtle (#f5f5f7 / #1c1c1e), and --bg-muted (#e8e8ed / #2c2c2e). The effect is architecturally minimal, like a white-walled gallery where the art (the poetry) is the focus.

   **Light and dark — cinematic, binary:** Light mode uses clean white and light gray (#f5f5f7) sections with Apple Blue as the singular accent. Dark mode uses pure black (#000000) — cinematic and immersive, not warm gray. Both themes use the same structural logic. In dark mode, Bright Blue (#2997ff) replaces Apple Blue (#003D74) for contrast against dark surfaces. The translucent glass navigation bar (`backdrop-filter: blur(20px)`) floats above content in both modes.

   **Interaction feel — precise and restrained:** Animations are subtle, fast, and functional — not decorative. Apple's motion language: things appear, they don't bounce. The brush strokes in Living Scroll mode are deliberate. The rating buttons respond with quiet confidence. The entire tempo communicates: this is not a game you rush through. This is practice.

2. **The "Living Scroll" interaction** — Instead of a binary flashcard flip, students reveal characters one by one on a virtual scroll with brush-stroke animations (via `hanzi-writer`). Completed scrolls are sealed with a blue chop stamp and saved to a personal gallery. Kids collect scrolls like trophies. This turns memorization into a calligraphy performance.

3. **Scientifically-backed spaced repetition with parent management** — Three algorithms (SM-2, Leitner, FSRS) with a parent-managed account model designed for young children who don't hold independent credentials.

## Constraints

- Web-first (Next.js), PWA-friendly, mobile-first responsive design
- Must run in Chromium-based browsers (Chrome/Edge) for future WebGPU/WebNN AI inference
- Parent/guardian accounts manage student profiles; students don't log in independently
- Poetry library is curated (~200-300 poems from PEP/HJ/SJ textbooks), not the full 55k+ corpus
- Polyphonic character handling is a core accuracy requirement — context-aware pinyin disambiguation via pypinyin
- Three-tier subscription model (Free / Pro / Max) — feature-to-tier mapping is flexible and decided per feature as they ship
- No Chinese social logins (WeChat, Alipay, QQ, Douyin) — all require 域名备案 (ICP filing)
- UI is multilingual (zh-CN, zh-TW, en, ja); classical Chinese poetry content is never translated
- Light and dark themes from day one
- Future: client-side AI inference via Transformers.js / ONNX Runtime Web (WebGPU/WebNN)
- Future: native mobile apps (React Native or native) with platform-specific ML runtimes
- Desktop: browser-only (no Tauri — WKWebView lacks WebNN support on macOS)

## Accessibility

- **Keyboard navigation:** All interactive elements (rating buttons, profile switcher, pinyin toggle, navigation) must be reachable and operable via keyboard. Living Scroll mode supports spacebar/enter to reveal next character
- **Screen readers:** ARIA labels on the Living Scroll canvas/SVG (announces poem title, current character position, and completion state). Rating buttons have descriptive labels ("Rate as Forgot", not just color). Scroll Gallery items announce poem title and completion date
- **Color contrast:** All text/background combinations must meet WCAG AA (4.5:1 for body text, 3:1 for large text). Tertiary text (#86868b) on white (#ffffff) is 3.5:1 — only use for large text (>18px) or decorative elements, never for essential body text. Secondary text (#6e6e73) on white is 4.6:1 (AA). Primary text (#1d1d1f) on white is 16.7:1 (AAA). Apple Blue (#003D74) on white is 4.5:1 (AA). Dark mode colors verified separately
- **Reduced motion:** Respect `prefers-reduced-motion: reduce`. When active: Living Scroll reveals characters instantly (no stroke animation), page transitions are instant, the chop stamp appears without animation. The "unhurried" aesthetic is a default, not a requirement
- **Touch targets:** All interactive elements ≥48x48px on mobile, per WCAG 2.5.8. Rating buttons and Ear Training tap zones are already large by design
- **Pinyin as accessible annotation:** `<ruby>/<rt>` markup is natively accessible to screen readers. The `lang="zh-Latn"` attribute on `<rt>` helps screen readers switch pronunciation engines

## Security Considerations

- **Input sanitization:** Custom poem content (user-supplied text) must be sanitized before rendering. The `<ruby>` markup is generated server-side from structured data (character + pinyin arrays), never from raw HTML input. Custom poem text fields accept plain text only; any HTML is escaped. Poem titles, author names, and content_lines are parameterized in all database queries
- **Rate limiting:** API routes `/api/pinyin` and `/api/pinyin-gen` (which shell out to Python via pypinyin) are rate-limited: 10 requests/minute per authenticated user, 2 requests/minute for unauthenticated. `/api/schedule` is rate-limited at 60 requests/minute per student profile. Implementation: Vercel Edge Middleware with `@upstash/ratelimit` or equivalent
- **RLS policy summary:** All Supabase tables use Row-Level Security. Key policies: (1) `students` — SELECT/UPDATE/DELETE only by linked guardians via `student_guardians` join. (2) `poem_reviews` / `fragment_reviews` — INSERT/UPDATE only for students linked to the current authenticated user. (3) `custom_poems` — owned by creator, visible only to linked guardians. (4) `profiles` / `users` — users can only read/update their own row. (5) `poems` / `poem_pinyin` — public read, admin-only write
- **Tier enforcement:** The `tierConfig` feature gate is enforced in both frontend (UI gating, upgrade prompts) and backend (API route middleware checks `users.plan` before executing paid-tier operations). Client-side checks are purely cosmetic; all tier-restricted actions are validated server-side. Supabase RLS policies can reference `users.plan` via a security-definer function for database-level enforcement
- **Child data protection:** Student profiles contain a child's name, grade, and learning history. No PII beyond what's necessary for the app's function. Student data is accessible only to linked guardians. Account deletion cascades to remove all student data. Consider COPPA/GDPR-K implications if expanding to US/EU markets

## Approaches Considered

### Approach A: Vite + React SPA + Supabase + Tauri
Rejected. Tauri uses WKWebView on macOS/iOS which lacks WebNN support. Since the project plans to use WebGPU/WebNN for client-side AI inference (Transformers.js / ONNX Runtime Web), Tauri cannot guarantee a Chromium engine across platforms.

### Approach B: Next.js + Supabase (web-first, PWA, mobile deferred)
**Selected.** Next.js App Router with Supabase for auth, Postgres, and row-level security. Server components for read-heavy pages (poetry library, analytics, admin). Client components for the learning session (cards, living scroll, WebGPU inference). API routes for pypinyin integration and future AI model serving. PWA for mobile-like experience. Native mobile apps (React Native or Swift/Kotlin) deferred until the web product is proven.

### Approach C: Web + Electron Desktop + React Native Mobile
Rejected as over-scoped for a fun/learning project. Electron adds 100MB+ for what's essentially a browser tab. Can revisit if desktop distribution becomes important.

### Key Implementation Details

**Authentication:**
- Five OAuth providers at launch: Google, Apple, GitHub, Microsoft — all free and native to Supabase. Plus email/password as universal fallback
- No Chinese social logins (WeChat, Alipay, QQ, Douyin). All require 域名备案 (ICP domain filing) which ties you to mainland China hosting. Not worth the bureaucratic overhead
- Phone SMS login deferred. Twilio (Supabase default) charges ~$0.05-0.08/msg to China. Domestic providers (Alibaba Cloud SMS, Tencent Cloud SMS) are ~¥0.04/msg but require custom SMS hook integration. Add only if users request it
- Transactional email (password reset, confirmation) via Resend as custom SMTP provider. 3,000 emails/month free tier, more than enough at launch. Configured in Supabase dashboard, no code changes
- Username/display name set during onboarding, stored in `profiles` table (decoupled from `auth.users`). Changeable in settings
- Profile schema: `profiles` table with `id` (FK to auth.users), `username` (unique), `display_name`, `locale`, `theme_preference`, `onboarding_completed`

**Internationalization (i18n):**
- UI language support: Simplified Chinese (zh-CN), Traditional Chinese (zh-TW), English (en), Japanese (ja) as the starting set. Additional locales can be added by dropping in a new translation file
- Uses `next-intl` with App Router integration (supports SSR, server components, middleware-based locale detection)
- Locale files per language in `messages/` directory (e.g., `messages/zh-CN.json`, `messages/en.json`)
- Detection priority: user preference in profile (if logged in) → browser `Accept-Language` → default to zh-CN
- What is NOT translated: poem text, pinyin, poet names, dynasty labels, classical Chinese annotations. These are the content, not the chrome
- What IS translated: menus, settings, onboarding flows, error messages, button labels, tooltips, empty states, notification copy, session summaries, analytics labels
- **zh-TW and character forms:** Poetry content is stored and displayed in simplified Chinese (简体字) only in v1. Traditional Chinese (zh-TW) users see simplified character poems — this is acceptable because the poems themselves are the canonical text, and most zh-TW readers can read simplified. Future: consider an OpenCC conversion layer to display poems in traditional characters for zh-TW locale users. This is a display-only transformation (stored simplified, rendered traditional) and does not affect pinyin or SRS state

**Theming (Light + Dark) — Apple-inspired:**
- Light theme: white (#ffffff) and light gray (#f5f5f7) surfaces, near-black (#1d1d1f) text. Primary: Apple Blue (#003D74). Content accent: coral (#ff6b6b) for polyphonic markers only
- Dark theme: pure black (#000000) surfaces with dark gray (#1c1c1e) elevated surfaces, near-white (#f5f5f7) text. Primary flips to Bright Blue (#2997ff) for contrast
- Semantic color tokens: `--bg`, `--bg-subtle`, `--bg-muted`, `--bg-card`, `--text`, `--text-secondary`, `--text-tertiary`, `--border`, `--border-subtle`, `--primary`, `--primary-hover`, `--primary-soft`, `--accent`, `--accent-hover`, `--accent-soft`, `--success` (Apple green #34c759), `--error` (Apple red #ff3b30), `--info` (Apple Blue), `--warning` (Apple orange #ea5414)
- Badge palette tokens: `--badge-1` (orange), `--badge-2` (blue), `--badge-3` (green), `--badge-4` (near-black/white)
- Implementation: Tailwind `darkMode: 'class'` + CSS variables + `next-themes` for toggle and persistence
- Glass navigation: `backdrop-filter: saturate(180%) blur(20px)` on translucent background — the signature Apple UI depth element
- System preference respected by default via `prefers-color-scheme`. User override stored in profile (`theme_preference`: system / light / dark)
- Toggle accessible from the glass navigation header (sun/moon icon)
- All color references in the app use CSS variables, never hardcoded hex values
- Apple Blue is the ONLY interactive accent color. No other chromatic hues for UI elements

**Profile Switching:**
- Header dropdown shows current student name + avatar
- Tap to expand list of all student profiles under this guardian
- Visual indicator (colored border) shows active student at all times
- Switching student reloads `currentStudentId` context and refreshes "晨光" (Today's Tasks)
- Settings changes are student-scoped; only the primary guardian (owner) can modify

**Living Scroll Mode:**
- Student sees an empty scroll with faint grid lines and the poem title
- Tapping reveals characters one by one with `hanzi-writer` stroke-order animation
- Correct reveals paint ink on rice paper (Canvas/SVG effect)
- Incorrect attempts show a red circle (traditional teacher correction mark)
- Completed scroll seals with a chop stamp (Apple Blue #003D74 light / Bright Blue #2997ff dark) bearing the student's name
- Scrolls save to a personal gallery (the gamification collection layer)
- After completion, student rates difficulty (Forgot/Hard/Good/Easy) for SRS scheduling
- **Performance strategy:** Lazy-load hanzi-writer only for the active character, preload next 3 characters in background, cache stroke data in IndexedDB after first render, provide "skip animation" fast-path for repeat reviews
- **Typography:** Use `heti heti--ancient heti--vertical` on the scroll container for authentic top-to-bottom, right-to-left text flow. In vertical mode, line breaks between verse lines are replaced with spaces — heti flows them as columns naturally. Pinyin appears to the left of each character (inline with the vertical flow), consistent with vertical ruby conventions.

**Pinyin System:**
- Public library: per-character rows in `poem_pinyin` table with AUTO/CONFIRMED status
- Custom poems: lightweight `pinyin_json` object
- Frontend: `<ruby><rb>字</rb><rp>(</rp><rt lang="zh-Latn">pinyin</rt><rp>)</rp></ruby>` inside a `heti heti--annotation` container. This is heti's official markup pattern: `<rb>` wraps the base character, `<rp>` provides fallback parentheses, `lang="zh-Latn"` on `<rt>` triggers correct font selection for pinyin. Zero whitespace between tags (whitespace creates text nodes that break ruby alignment). Pinyin toggle via `.pinyin-hidden rt { display: none }` class on `<html>`
- Equal-width character spacing: poetry containers use `display: inline-flex; flex-direction: column-reverse; width: 1.8em` on `ruby` elements so every character occupies the same horizontal space regardless of pinyin length. `<rp>` is `display: none`, `<rb>` and `<rt>` are `display: block`. Long pinyin overflows visually without pushing characters apart (standard CJK typesetting approach)
- Vertical mode (`heti--vertical`): same flex approach with fixed `height: 1.8em` instead of width. `flex-direction: column-reverse` puts pinyin to the right of each character
- Polyphonic characters marked with `data-polyphone="true"` on the `<ruby>` element so the editor can surface them for manual review. Polyphonic pinyin renders in coral (#ff6b6b) content accent color

**Pinyin Visibility — two layers of control:**

Students have different abilities. Some no longer need pinyin by 2nd grade, others still rely on it in 5th grade. The design respects this with two complementary controls:

1. **Per-student default (Settings):** "Show pinyin" toggle (On/Off), stored in `students.settings_json`. The parent or primary guardian sets this based on the child's ability. This value initializes `--pinyin-display` to `block` or `none` on every session start.

2. **Quick session toggle (Poem display):** A small, unobtrusive eye icon in the poem header. One tap flips pinyin visibility instantly for the current session via the CSS variable — no re-render, no API call. This is a session-only override; it does not change the saved setting. Next session reverts to the default. This lets a confident student hide pinyin to test themselves, or a struggling student peek at pinyin on a hard poem, without touching settings.

The CSS variable approach means the toggle is instant across all visible poem text, pinyin in the Living Scroll, and pinyin in the Ear Training screen's "now playing" display (if the student glances at it). One variable, every `<rt>` tag responds.

**Poetry Rendering — Heti Integration:**

Heti (`npm install heti`) is purpose-built CSS for Chinese typesetting. It replaces a pile of custom CSS hacks with a composable class system:

- `heti--ancient` — centered verse lines, full-width punctuation compressed to proper optical width, dynasty/author metadata styling via `heti-meta`
- `heti--annotation` — grid-aligned interlinear ruby so `<rt>` sits at consistent height above every base character, no browser-default misalignment
- `heti-hang` — hanging punctuation: sentence-ending marks (，。！？) sit outside the text block, matching classical print convention
- `heti--vertical` — top-to-bottom text flow for Living Scroll and Scroll Gallery; columns run right-to-left

**Pinyin toggle — class-based, not display:**

```css
/* globals.css */

/* IMPORTANT: never set display on rt — browser must keep native
   display:ruby-text so <rt> renders above the character, not beside it.
   display:block or display:var(..., block) breaks ruby positioning. */

.pinyin-hidden rt {
  display: none;
}
```

```ts
// One classList toggle, all <rt> elements across the page respond —
// no React state, no re-render, no layout shift on reveal
document.documentElement.classList.toggle('pinyin-hidden', !showPinyin)
```

Setting `display: block` (or any non-`ruby-text` value) on `<rt>` collapses the annotation inline beside the character instead of above it. The class-based toggle avoids touching the display property at all when pinyin is visible; `display: none` when hidden is safe because the ruby container collapses cleanly.

**拾诗 — Custom Poem Autocomplete (paid tier: Pro/Max):**

When a paid-tier parent creates a custom poem, they shouldn't have to manually type dynasty, author, and full text for well-known poems. The title field has intelligent autocomplete powered by the full `chinese-poetry` dataset (55,000+ Tang poems, 260,000+ Song poems, 21,000+ Song ci).

*Interaction flow:*
- Parent starts typing in the title field. After 1 character, a dropdown appears with fuzzy-matched results
- Each dropdown item shows: **poem title** + author + dynasty, in a compact row. The title match is highlighted (bold the matching characters)
- Results are ranked: exact prefix matches first, then fuzzy matches. Limit to 8 visible results with scroll for more
- Selecting a result auto-fills all fields: title, dynasty, author, and complete poem text (line by line into `content_lines`)
- After auto-fill, the parent reviews the text (in case of variant editions) and clicks "Generate Pinyin" as normal
- The parent can still type a completely custom title that doesn't match any known poem — the autocomplete is a convenience, not a gate

*Search index implementation:*
- Build a lightweight search index from the `chinese-poetry` JSON dataset at build time. Extract only title + author + dynasty + content for each poem. This is a static asset, not a database query.
- Index format: a compressed JSON file (~5-10MB for the full corpus) or a pre-built search index using a client-side search library like `fuse.js` (fuzzy search) or `flexsearch` (faster, prefix-optimized). `flexsearch` is recommended — it's ~6KB gzipped, supports Chinese tokenization, and handles prefix matching well.
- The index loads lazily on the custom poem creation page (not on every page load). Once loaded, searches are instant (<10ms) with no network round-trip.
- The full poem text is NOT stored in the search index (too large). The index stores title + author + dynasty + a content hash. When the user selects a match, fetch the full poem content from a separate static JSON asset, keyed by ID. This keeps the search index small and the content fetch fast.

*Why not an external API:*
- The `chinese-poetry` dataset is already a project dependency (MIT license)
- No network latency, no API rate limits, no cost, works offline
- You control data quality and can update the dataset on your own schedule
- A static search index is faster than any API call

**Spaced Repetition Engine:**
- Unified scheduling: poems and fragments both query `next_review_at <= now()`
- SM-2: ~40 lines core algorithm, ~200 lines total with unified scheduler integration
- Leitner: ~30 lines core algorithm, simpler state (box level + interval)
- FSRS: `ts-fsrs` npm package, paid tier only (Pro or Max, TBD). Free users see it locked with upgrade prompt
- SRS Scheduler Service (~300 LOC total): unified next_review_at query across poems + fragments, rating submission handler, algorithm factory/strategy pattern, migration logic, edge case handling (deleted poems, archived students)
- FSRS migration: reads the full review history from `poem_reviews` and recalculates state using the FSRS formula, preserving all past ratings while computing new stability/difficulty values. Existing `next_review_at` is honored until the next evaluation, then FSRS takes over scheduling
- Guardian conflict resolution: algorithm preference is stored on the `students` record (single source of truth). Only the primary guardian (owner) can change it. Non-owner guardians see read-only settings

**Gamification — quiet, never intrusive:**

The core principle: gamification exists to reward consistency, not to interrupt focus. A child in the middle of memorizing a poem should never be pulled out of that flow by a popup, a confetti animation, or a "You earned 10 points!" banner. The learning session is sacred. Rewards happen at the boundaries, not during.

- **During a review session: zero interruptions.** No popups, no toasts, no point counters ticking up, no "streak at risk!" warnings. The only visual feedback is the Living Scroll completion (the chop stamp seal), which is part of the learning interaction itself, not a gamification overlay. Points and progress accrue silently in the background.
- **After a session ends: a calm summary.** The session completion screen shows what was accomplished — poems reviewed, accuracy, streak status — in the same quiet aesthetic as the rest of the app. No fireworks. Think of it like closing a book and seeing a ribbon bookmark marking your progress. A small, warm moment of "well done" that matches the unhurried tempo of the app.
- **Scroll Gallery as the primary collection layer.** Completed Living Scroll works are saved to a personal gallery. This is the most visible gamification, but it doesn't feel like gamification — it feels like a child's portfolio of calligraphy practice. Scrolls are beautiful objects in themselves. Collecting them is intrinsically satisfying the way filling a bookshelf is.
- **Streak counter: visible on the home screen, never nagging.** A simple "Day 14" with a small flame or ink-drop icon. No "Don't break your streak!" push notifications. No anxiety-inducing countdown. If the streak breaks, it resets quietly. The parent can see streak history in analytics; the student just sees today's number.
- **Badges: discovered, not announced.** Milestones (10 poems mastered, 30-day streak, all Grade 1 poems complete) unlock badges that appear in a profile section. The student discovers them when they visit their profile, like finding a stamp in a passport. No mid-session interruption, no modal, no sound effect. The parent sees new badges in their analytics dashboard.
- **No points system.** Points are the most addictive and least meaningful gamification mechanic. They train children to optimize for points instead of actual recall. Kuibu tracks mastery (poems at SRS stability > N days) and consistency (streak length), not an arbitrary score. If a numerical metric is needed, it's "poems mastered" — a real count of real achievement.

**Parent Analytics:**
- Review completion rates per student
- Memory retention curves (predicted retrievability over time)
- Study frequency heatmap (calendar view)
- Per-poem mastery status
- Comparative progress across students

**Audio/TTS — fully client-side, no cloud AI:**

No cloud TTS services (Azure, Google, etc.). Audio generation runs entirely in the browser via Transformers.js with a speech synthesis model accelerated by WebGPU or WebNN.

- **Primary path:** Transformers.js loads a Chinese-capable speech model (e.g., MMS-TTS, SpeechT5, or Kokoro-based models with Chinese support) and runs inference on-device via WebGPU/WebNN. The model is downloaded once and cached in the browser (IndexedDB or Cache API). Subsequent poem recitations are instant with no network dependency.
- **Fallback:** Web Speech API (`speechSynthesis`) for browsers that lack WebGPU support. Quality varies by OS/browser, but it's functional and requires zero setup. The app detects WebGPU availability at startup and routes accordingly.
- **UX:** Play button on poem display. Optional auto-play in settings. During Living Scroll mode, audio can play the full poem before the student begins the character reveal, setting the auditory memory before the recall test.
- **Model selection criteria:** Must support Mandarin Chinese with accurate tonal pronunciation. Model size should be under ~100MB for reasonable first-load experience. Quantized (INT8/INT4) models preferred for faster inference and smaller downloads.
- **This is the first real use of the WebGPU/WebNN infrastructure** that justified the Chromium-only constraint. TTS ships before any other AI feature, proving the client-side inference pipeline on a concrete, high-value use case.

**Ear Training — two listening modes (沉浸听诵 + 听诵复习):**

This feature lets students learn and review poems by voice alone, without looking at a screen. It's ideal for car rides, falling asleep, doing chores, walking, or any situation where eyes and hands are occupied. Both modes build on the same Transformers.js TTS engine.

*Passive Listening (沉浸听诵) — no interaction, pure immersion:*

- The app plays through today's due poems as continuous audio, like a playlist
- **SRS-weighted repetition:** Poems are not played equally. The loop weights frequency by SRS stability — poems with low stability (struggling, short review intervals) play 2-3x per cycle, while mastered poems (high stability, long intervals) play once. This creates a spaced-repetition effect through exposure frequency alone, even without explicit ratings
- **Poem structure per play:** Title announced first ("静夜思, 李白"), brief pause (1s), then the full poem read at a measured, recitation-appropriate pace. Between poems, a 3-second silence so the student can mentally echo what they just heard
- **Loop behavior:** After all due poems play once (weighted), the cycle repeats. Configurable in settings: loop N times, loop for N minutes, or loop until stopped
- **Background audio:** Uses the Web Audio API and Media Session API so playback continues when the phone is locked or the browser tab is backgrounded. Lock screen shows "Kuibu — Listening" with poem title, play/pause, and skip controls
- **Wake Lock API:** Prevents the device from sleeping during a listening session
- **No SRS state changes.** Passive listening is exposure, not assessment. Review state is unaffected. The parent analytics dashboard can show "listening time" as a separate metric from "active review"

*Active Listening (听诵复习) — audio-only spaced repetition:*

- Same audio flow as passive mode: title announcement, poem recitation
- After the poem finishes, a distinct soft chime (not jarring — a wooden block knock 木鱼 or a gentle bell, matching the aesthetic) signals "rate your recall now"
- The app waits for a rating via three input channels, whichever comes first:

  **Channel 1 — Voice command (primary for hands-free, requires network):**
  Web Speech API `SpeechRecognition` (on-device in Chrome). **Note:** Despite Chrome labeling this as "on-device," most Chromium builds still send audio to Google servers for processing. Voice commands require network connectivity. In offline scenarios, headphone button taps (Channel 2) are the primary input method. The active vocabulary is just 4 words, so recognition accuracy is very high when online. Supported commands:
  - "淡忘" or "forgot" → Forgot
  - "艰难" or "hard" → Hard
  - "尚可" or "good" → Good
  - "轻松" or "easy" → Easy
  Continuous listening mode with a 10-second timeout. If no command recognized within 10s, auto-rate as "Good" (configurable default in settings) and move on, so the session never stalls.

  **Channel 2 — Headphone button taps (best for noisy environments):**
  Media Session API maps physical headphone buttons:
  - Single tap → Good (the most common rating, lowest friction)
  - Double tap → Easy
  - Triple tap → Hard
  - Long press → Forgot
  Works with any Bluetooth headphones or wired earbuds with inline controls. More reliable than voice in noisy environments (bus, street, kitchen).

  **Channel 3 — Screen tap (fallback):**
  Minimal lock-screen-style UI with four large, high-contrast tap zones filling the screen. Designed for a quick glance-and-tap without reading. The four zones use the app's color language: a muted tone for Forgot, neutral tones graduating to green (#34c759) for Easy.

- After rating: SRS state updates exactly as in the visual review modes (same algorithm, same scheduling). Next poem plays immediately.
- **Session summary:** When all due poems are reviewed (or session is stopped), a brief audio summary: "Today's listening review complete. N poems reviewed." The visual session summary shows the same calm report as visual review sessions.

*Shared infrastructure for both modes:*

- **Playlist generation:** On session start, query all poems where `next_review_at <= now()` for the current student. Order by priority: lowest stability first (these need the most reinforcement). In passive mode, assign repetition weights. In active mode, play each once.
- **Offline capability:** Since TTS runs on-device via Transformers.js, and the poem text is cached locally, ear training works without network once the TTS model is downloaded. SRS state sync (active mode ratings) queues locally in IndexedDB and syncs when reconnected (see Design Decision #2 for scope). Voice commands (Channel 1) require network; headphone taps (Channel 2) and screen taps (Channel 3) work fully offline.
- **Parent controls:** Settings include max listening session duration (default: 30 min), active mode timeout behavior (auto-rate or pause), and whether to include fragments in listening sessions (Chinese fragments only, not English).
- **Analytics:** Parent dashboard shows listening minutes per day, passive vs active split, and for active mode, the same accuracy/retention metrics as visual review.

## Design Decisions (resolved)

1. **Living Scroll = review event.** Scroll completion is an alternative review mode, not separate practice. Completing the scroll triggers the same Forgot/Hard/Good/Easy rating and updates SRS state. This avoids dual accounting complexity and treats the scroll as a more engaging flashcard flip. Students choose their preferred mode (scroll or card flip) per session.

2. **Offline scope: installable PWA, no offline reviews in v1 (with ear training exception).** PWA provides installable icon, splash screen, and cached static assets. Offline reviews require client-side scheduling and sync reconciliation which conflicts with the Supabase RLS model. V2 can add full offline review with optimistic local state and server reconciliation on reconnect. **Exception:** Ear Training Active Listening can queue SRS ratings locally (IndexedDB) and sync on reconnect, because its linear playlist flow avoids scheduling conflicts — the next poem is already determined at session start, so no client-side scheduling recalculation is needed mid-session. This is a narrow carve-out, not a general offline review capability.

3. **Hosting pypinyin: batch at build time, API route for custom poems only.** The curated library pinyin is generated once via a Python batch script and stored in the database. Only custom poem creation (paid feature) calls the pypinyin API route at runtime. Fallback: if API fails, allow manual pinyin entry with a "retry auto-generation" button.

4. **FSRS visibility: visible to all, selectable by paid tier only.** Free users see FSRS in the algorithm picker with a lock icon and upgrade prompt. This serves as a natural upsell touchpoint without hiding functionality.

5. **Subscription model: three tiers (Free / Pro / Max), feature mapping flexible.** The `users.plan` field uses an enum that supports FREE, PRO, MAX (and ADMIN). Feature-to-tier gating is enforced in backend middleware via a config map, making it easy to move features between tiers without schema changes. Specific tier assignments for each feature (FSRS algorithm, custom poems, advanced analytics, higher quotas, etc.) will be decided as features ship and usage patterns emerge. Start without payment integration. Manually toggle tiers via Supabase admin. Add Stripe when there are users who want to pay.

6. **Tier config approach:** A single `tierConfig` object maps feature keys to minimum required plan. For example: `{ fsrs: 'PRO', customPoems: 'PRO', advancedAnalytics: 'MAX', maxStudents: { FREE: 2, PRO: 8, MAX: 120 } }`. This config is shared between frontend (UI gating, upgrade prompts) and backend (middleware enforcement). Changing which tier unlocks a feature is a one-line config change, not a code change.

7. **Auth: no Chinese social logins, no ICP filing.** WeChat/Alipay/QQ/Douyin all require 域名备案 (ICP domain filing) which ties the app to mainland China hosting and bureaucratic overhead. Not worth it. Email + Google + Apple + GitHub + Microsoft covers the audience. Phone SMS deferred due to cost ($0.05-0.08/msg via Twilio to China; domestic providers cheaper but require custom integration).

8. **i18n from day one, content stays Chinese.** UI supports zh-CN, zh-TW, en, ja via `next-intl`. Poetry text, pinyin, poet names, and dynasty labels are never translated. Retrofitting i18n later is painful; the string extraction cost at day one is near-zero.

9. **Light + dark theme from day one.** CSS variables + `next-themes` + Tailwind `darkMode: 'class'`. Apple-inspired: light = white/#f5f5f7 with Apple Blue primary, dark = pure black/#1c1c1e with Bright Blue primary. Glass navigation in both modes. Retrofitting dark mode into an existing color system is one of the worst kinds of tech debt. Setting it up at scaffold time is free.

10. **Resend for transactional email.** Supabase's built-in email is rate-limited (2/hr free, 100/hr Pro). Resend gives 3,000 emails/month free, which covers password reset and confirmation at launch scale. Dashboard-only config, no code changes.

## Error States & Empty States

**晨光 (Today's Tasks) — no poems due:**
- Empty state: A calm illustration (ink wash style, minimal) with the message "今日无诗可复习" / "No poems to review today." Below: a subtle suggestion — "Browse the poetry library to add new poems" with a link to 诗库. The screen should feel restful, not broken. The student has earned a day off; the design should reflect that.

**Living Scroll — hanzi-writer fails to load stroke data:**
- If stroke data for a character is unavailable (rare characters outside hanzi-writer's ~9,000 character coverage), fall back to displaying the character as static text with a fade-in animation instead of stroke-by-stroke. Log the missing character for the admin to review. Do not block the scroll — skip the animation, show the character, and continue.

**TTS model download failure:**
- If the Transformers.js model fails to download (network error, storage full), show a non-blocking toast: "语音模型下载失败，使用系统朗读" / "Speech model download failed, using system voice." Auto-fall back to Web Speech API. If Web Speech API also has no Chinese voice available, disable the play button with a tooltip explaining why. Ear Training modes show a clear message before session start if no TTS is available.

**Web Speech API fallback quality:**
- When using the Web Speech API fallback (no WebGPU), the quality varies significantly by OS. Add a small info icon next to the play button that explains: "当前使用系统语音，效果因设备而异" / "Using system voice, quality varies by device." Do not present this as an error — it's a graceful degradation.

**Network failure during review session:**
- If network drops mid-review, current ratings are queued in memory and shown as "pending sync" with a subtle cloud-with-arrow icon. The session continues uninterrupted — the student can finish all due reviews. On next network availability, queued ratings sync automatically. If the app is closed before sync, pending ratings are lost (acceptable in v1; v2's offline support addresses this with IndexedDB persistence). Exception: Ear Training Active Listening already persists to IndexedDB per Design Decision #2.

**Profile switching — no students created:**
- If a guardian has not created any student profiles, the profile switcher shows the onboarding CTA: "创建第一个学生档案" / "Create your first student profile." This state only occurs before onboarding is completed.

**Custom poem pinyin generation failure:**
- If the `/api/pinyin-gen` route fails (pypinyin error, timeout, rate limit), show the generated fields as "待生成" / "Pending" and enable manual pinyin entry. A "重试自动生成" / "Retry auto-generation" button is available. The parent can always save a custom poem with manually entered pinyin.
