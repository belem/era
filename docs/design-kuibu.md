## Problem Statement

Classical Chinese poetry memorization is a core part of primary and middle school education in China, but existing tools are either pure reference apps (browse/search) or gamified quiz apps with no scientific scheduling. Anki has spaced repetition but zero cultural aesthetics and is intimidating for parents and young children. There's a gap for a beautifully designed, parent-managed, scientifically-backed poetry memorization platform that respects the cultural weight of the material.

## What Makes This Cool

The intersection of three things no one is combining well:

1. **Traditional Chinese aesthetics as a first-class design principle** — The app should feel like stepping into a scholar's study (书房), not opening a flashcard deck. Every design choice draws from centuries of Chinese visual culture, but filtered through modern restraint.

   **Color philosophy — the five ink tones (墨分五色):** Chinese painting teaches that ink alone contains five colors: burnt (焦), concentrated (浓), heavy (重), light (淡), and clear (清). The palette follows this principle. The primary surface is not flat white but a warm, living tone — think aged Xuan paper that has yellowed slightly with time, somewhere between raw silk and morning fog. Text is never pure black (#000) but ink-black with warmth, the color of fresh ink ground on a stone with a few drops of water. Accent colors are drawn from traditional mineral pigments, not digital primaries: vermillion (朱砂红) for primary actions and celebration moments, stone blue (石青) for navigation and structural elements, and a muted gold (赭石) that appears only on earned achievements — the color of imperial seals. The overall effect should feel like a Song dynasty painting: restrained, with vast breathing room, where a single stroke of red carries enormous weight precisely because everything else is quiet.

   **Typography — three voices, carefully paired:**

   The app speaks in three typographic registers. Each one is chosen for a reason that goes beyond "looks nice."

   **Voice 1 — Poetry body: LXGW WenKai (霞鹜文楷)**, loaded from Google Fonts. This is the heart of the app's type identity. Kai (楷) is the style Chinese children learn to write by hand in school. Every stroke in LXGW WenKai follows the structure a teacher would demonstrate on a blackboard: clear entry and exit strokes, balanced proportions, warmth without looseness. It bridges reading and writing practice, so a child seeing "床前明月光" in LXGW WenKai is also subconsciously reinforcing how those characters should be handwritten. Technically: it has excellent CJK coverage (~8,000 characters), multiple weights (Regular and Light at minimum), and is open source (SIL license). Load Regular (400) for poem body and Light (300) for longer prose passages in the fragment module. Set `font-feature-settings: "kern" 1` and track letter-spacing at 0.05em for poetry lines to give each character room to breathe.

   **Voice 2 — Headings and structure: Noto Serif SC** (思源宋体), loaded from Google Fonts. Song/Ming style (宋体) carries the authority of printed books. It's what you see on the title page of a classical collection, the spine of a thread-bound volume (线装书). The vertical strokes are thin, the horizontal strokes have weight, and the serifs (顿笔) give each character a sense of being placed, not typed. Use SemiBold (600) for page titles and section headers, Regular (400) for secondary headings like dynasty/author labels. The contrast between Kai (handwritten warmth) for poetry and Song (printed authority) for structure creates a natural visual hierarchy without needing size differences alone. This pairing has centuries of precedent in Chinese book design, where the cover is Song and the interior is Kai.

   **Voice 3 — UI and pinyin: system sans-serif + Inter.** Buttons, navigation, labels, timestamps, and all functional text use the system's native sans-serif stack: `"PingFang SC", "Microsoft YaHei", "Noto Sans SC", system-ui, sans-serif`. This is intentionally invisible typography. It loads instantly (no web font download), it's what users read every day on their devices, and it signals "this is the app talking to you" as distinct from "this is the poetry." For pinyin annotations above characters and any Latin text (email addresses, URLs, version numbers), use Inter (Google Fonts) — its x-height and letter spacing are optimized for small sizes and it pairs cleanly with both LXGW WenKai and Noto Serif. Pinyin renders at roughly 45% of the character's font size, in a lighter color (not the same ink-black as the character itself), sitting above like a teacher's pencil note — present when you need it, easy to ignore when you don't.

   **Font loading strategy:** LXGW WenKai is the largest download (~4-6MB for SC Regular). Use `font-display: swap` with a system Kai fallback (`"KaiTi", "STKaiti", "AR PL UKai"`) so the page is readable immediately and switches to the web font when loaded. Noto Serif SC is lighter (~2MB subset for common characters). Inter is tiny (~100KB variable). Preload LXGW WenKai Regular in the document `<head>` since it's critical for the first meaningful paint of any poetry page. Consider subsetting to the ~3,000 most common characters for initial load, with the full set loaded lazily.

   **Space — the art of leaving blank (留白):** Classical Chinese composition prizes negative space as much as the mark. A poem of twenty characters should feel like it's floating in open air, not crammed into a card. Generous margins. Vertical rhythm that lets each line breathe. The screen should never feel full. When in doubt, remove, don't add. This is the hardest design discipline and the one that will most distinguish Kuibu from every other education app.

   **Texture and material — felt, not seen:** Subtle paper grain on primary surfaces, visible only at certain angles or on close inspection — not a loud skeuomorphic texture slapped over the UI, but a quiet physical quality that makes the screen feel less like glass. Soft shadows that suggest layered paper rather than floating cards. Transitions that feel like pages turning or scrolls unrolling, with the slight resistance of real paper, not the frictionless sliding of generic app animations.

   **Light and mood — the study lamp:** The overall atmosphere is a warm evening study session. Soft, amber-tinted warmth rather than the cold blue light of most apps. Dark mode, when implemented, should feel like reading by candlelight or moonlight — the classic poetry scenario — not like a generic dark theme. The palette shifts to deep indigo and warm ivory, the colors of a moonlit window with rice paper screens.

   **Interaction feel — unhurried:** Every animation runs slightly slower than a typical app. Not sluggish, but deliberate. The brush strokes in Living Scroll mode take the time a real brush would take. Page transitions have the weight of turning thick paper. The rating buttons after a review don't bounce or flash — they respond with the quiet confidence of a well-made physical button. The entire tempo communicates: this is not a game you rush through. This is practice. Practice has its own pace.

2. **The "Living Scroll" interaction** — Instead of a binary flashcard flip, students reveal characters one by one on a virtual scroll with brush-stroke animations (via `hanzi-writer`). Completed scrolls are sealed with a vermillion chop stamp and saved to a personal gallery. Kids collect scrolls like trophies. This turns memorization into a calligraphy performance.

3. **Scientifically-backed spaced repetition with parent management** — Three algorithms (SM-2, Leitner, FSRS) with a parent-managed account model designed for young children who don't hold independent credentials.

## Constraints

- Web-first (Next.js), PWA-friendly, mobile-first responsive design
- Must run in Chromium-based browsers (Chrome/Edge) for future WebGPU/WebNN AI inference
- Parent/guardian accounts manage student profiles; students don't log in independently
- Poetry library is curated (~200-300 poems from PEP/HJ/SJ textbooks), not the full 55k+ corpus
- Polyphonic character handling is a core accuracy requirement — context-aware pinyin disambiguation via pypinyin
- Three-tier subscription model (Free / Pro / Max) — feature-to-tier mapping is flexible and decided per feature as they ship
- Future: client-side AI inference via Transformers.js / ONNX Runtime Web (WebGPU/WebNN)
- Future: native mobile apps (React Native or native) with platform-specific ML runtimes
- Desktop: browser-only (no Tauri — WKWebView lacks WebNN support on macOS)

## Approaches Considered

### Approach A: Vite + React SPA + Supabase + Tauri
Rejected. Tauri uses WKWebView on macOS/iOS which lacks WebNN support. Since the project plans to use WebGPU/WebNN for client-side AI inference (Transformers.js / ONNX Runtime Web), Tauri cannot guarantee a Chromium engine across platforms.

### Approach B: Next.js + Supabase (web-first, PWA, mobile deferred)
**Selected.** Next.js App Router with Supabase for auth, Postgres, and row-level security. Server components for read-heavy pages (poetry library, analytics, admin). Client components for the learning session (cards, living scroll, WebGPU inference). API routes for pypinyin integration and future AI model serving. PWA for mobile-like experience. Native mobile apps (React Native or Swift/Kotlin) deferred until the web product is proven.

### Approach C: Web + Electron Desktop + React Native Mobile
Rejected as over-scoped for a fun/learning project. Electron adds 100MB+ for what's essentially a browser tab. Can revisit if desktop distribution becomes important.

## Recommended Approach

**Next.js + Supabase, web-first, PWA-ready, mobile deferred.**

### Key Implementation Details

**Onboarding Flow:**
1. Parent creates account (email + password via Supabase Auth)
2. Welcome screen: "Create your first student profile" — name, grade, textbook edition
3. Algorithm selection with visual explanation: Leitner (simple boxes, recommended for younger kids), SM-2 (classic, recommended default), FSRS (advanced, paid tier)
4. Quick intro to Living Scroll mode (3-second animation demo)
5. First review session begins immediately with 5 pre-selected famous poems

**Profile Switching:**
- Header dropdown shows current student name + avatar
- Tap to expand list of all student profiles under this guardian
- Visual indicator (colored border) shows active student at all times
- Switching student reloads `currentStudentId` context and refreshes "Today's Tasks"
- Settings changes are student-scoped; only the primary guardian (owner) can modify

**Living Scroll Mode:**
- Student sees an empty scroll with faint grid lines and the poem title
- Tapping reveals characters one by one with `hanzi-writer` stroke-order animation
- Correct reveals paint ink on rice paper (Canvas/SVG effect)
- Incorrect attempts show a red circle (traditional teacher correction mark)
- Completed scroll seals with a vermillion chop stamp bearing the student's name
- Scrolls save to a personal gallery (the gamification collection layer)
- After completion, student rates difficulty (Forgot/Hard/Good/Easy) for SRS scheduling
- **Performance strategy:** Lazy-load hanzi-writer only for the active character, preload next 3 characters in background, cache stroke data in IndexedDB after first render, provide "skip animation" fast-path for repeat reviews

**Pinyin System:**
- Public library: per-character rows in `poem_pinyin` table with AUTO/CONFIRMED/DISPUTED status
- Custom poems: lightweight `pinyin_json` object
- Frontend: `<ruby>/<rt>` tags with CSS variable `--pinyin-display` toggle

**Pinyin Visibility — two layers of control:**

Students have different abilities. Some no longer need pinyin by 2nd grade, others still rely on it in 5th grade. The design respects this with two complementary controls:

1. **Per-student default (Settings):** "Show pinyin" toggle (On/Off), stored in `students.settings_json`. The parent or primary guardian sets this based on the child's ability. This value initializes `--pinyin-display` to `block` or `none` on every session start.

2. **Quick session toggle (Poem display):** A small, unobtrusive eye icon in the poem header. One tap flips pinyin visibility instantly for the current session via the CSS variable — no re-render, no API call. This is a session-only override; it does not change the saved setting. Next session reverts to the default. This lets a confident student hide pinyin to test themselves, or a struggling student peek at pinyin on a hard poem, without touching settings.

The CSS variable approach means the toggle is instant across all visible poem text, pinyin in the Living Scroll, and pinyin in the Ear Training screen's "now playing" display (if the student glances at it). One variable, every `<rt>` tag responds.
- Long-press character: "Report Error" (system poems) or "Edit Pinyin" (custom poems)

**Custom Poem Autocomplete (paid tier: Pro/Max):**

When a paid-tier parent creates a custom poem, they shouldn't have to manually type dynasty, author, and full text for well-known poems. The title field has intelligent autocomplete powered by the full `chinese-poetry` dataset (55,000+ Tang poems, 260,000+ Song poems, 21,000+ Song ci).

*Interaction flow:*
- Parent starts typing in the title field. After 1 character, a dropdown appears with fuzzy-matched results
- Each dropdown item shows: **poem title** + author + dynasty, in a compact row. The title match is highlighted (bold the matching characters)
- Results are ranked: exact prefix matches first, then fuzzy matches. Limit to 8 visible results with scroll for more
- Selecting a result auto-fills all fields: title, dynasty, author, and complete poem text (line by line into `content_lines`)
- After auto-fill, the parent reviews the text (in case of variant editions) and clicks "Generate Pinyin" as normal
- The parent can still type a completely custom title that doesn't match any known poem — the autocomplete is a convenience, not a gate

*Search index implementation:*
- Build a lightweight search index from the `chinese-poetry` JSON dataset at build time. Extract only title + author + dynasty + content for each poem. This is a static asset, not a database query.
- Index format: a compressed JSON file (~5-10MB for the full corpus) or a pre-built search index using a client-side search library like `fuse.js` (fuzzy search) or `flexsearch` (faster, prefix-optimized). `flexsearch` is recommended — it's ~6KB gzipped, supports Chinese tokenization, and handles prefix matching well.
- The index loads lazily on the custom poem creation page (not on every page load). Once loaded, searches are instant (<10ms) with no network round-trip.
- The full poem text is NOT stored in the search index (too large). The index stores title + author + dynasty + a content hash. When the user selects a match, fetch the full poem content from a separate static JSON asset, keyed by ID. This keeps the search index small and the content fetch fast.

*Why not an external API:*
- The `chinese-poetry` dataset is already a project dependency (MIT license)
- No network latency, no API rate limits, no cost, works offline
- You control data quality and can update the dataset on your own schedule
- A static search index is faster than any API call

**Spaced Repetition Engine:**
- Unified scheduling: poems and fragments both query `next_review_at <= now()`
- SM-2: ~40 lines core algorithm, ~200 lines total with unified scheduler integration
- Leitner: ~30 lines core algorithm, simpler state (box level + interval)
- FSRS: `ts-fsrs` npm package, paid tier only (Pro or Max, TBD). Free users see it locked with upgrade prompt
- SRS Scheduler Service (~300 LOC total): unified next_review_at query across poems + fragments, rating submission handler, algorithm factory/strategy pattern, migration logic, edge case handling (deleted poems, archived students)
- FSRS migration: reads the full review history from `poem_reviews` and recalculates state using the FSRS formula, preserving all past ratings while computing new stability/difficulty values. Existing `next_review_at` is honored until the next evaluation, then FSRS takes over scheduling
- Guardian conflict resolution: algorithm preference is stored on the `students` record (single source of truth). Only the primary guardian (owner) can change it. Non-owner guardians see read-only settings

**Gamification — quiet, never intrusive:**

The core principle: gamification exists to reward consistency, not to interrupt focus. A child in the middle of memorizing a poem should never be pulled out of that flow by a popup, a confetti animation, or a "You earned 10 points!" banner. The learning session is sacred. Rewards happen at the boundaries, not during.

- **During a review session: zero interruptions.** No popups, no toasts, no point counters ticking up, no "streak at risk!" warnings. The only visual feedback is the Living Scroll completion (the chop stamp seal), which is part of the learning interaction itself, not a gamification overlay. Points and progress accrue silently in the background.
- **After a session ends: a calm summary.** The session completion screen shows what was accomplished — poems reviewed, accuracy, streak status — in the same quiet aesthetic as the rest of the app. No fireworks. Think of it like closing a book and seeing a ribbon bookmark marking your progress. A small, warm moment of "well done" that matches the unhurried tempo of the app.
- **Scroll Gallery as the primary collection layer.** Completed Living Scroll works are saved to a personal gallery. This is the most visible gamification, but it doesn't feel like gamification — it feels like a child's portfolio of calligraphy practice. Scrolls are beautiful objects in themselves. Collecting them is intrinsically satisfying the way filling a bookshelf is.
- **Streak counter: visible on the home screen, never nagging.** A simple "Day 14" with a small flame or ink-drop icon. No "Don't break your streak!" push notifications. No anxiety-inducing countdown. If the streak breaks, it resets quietly. The parent can see streak history in analytics; the student just sees today's number.
- **Badges: discovered, not announced.** Milestones (10 poems mastered, 30-day streak, all Grade 1 poems complete) unlock badges that appear in a profile section. The student discovers them when they visit their profile, like finding a stamp in a passport. No mid-session interruption, no modal, no sound effect. The parent sees new badges in their analytics dashboard.
- **No points system.** Points are the most addictive and least meaningful gamification mechanic. They train children to optimize for points instead of actual recall. Kuibu tracks mastery (poems at SRS stability > N days) and consistency (streak length), not an arbitrary score. If a numerical metric is needed, it's "poems mastered" — a real count of real achievement.

**Parent Analytics:**
- Review completion rates per student
- Memory retention curves (predicted retrievability over time)
- Study frequency heatmap (calendar view)
- Per-poem mastery status
- Comparative progress across students

**Audio/TTS — fully client-side, no cloud AI:**

No cloud TTS services (Azure, Google, etc.). Audio generation runs entirely in the browser via Transformers.js with a speech synthesis model accelerated by WebGPU or WebNN.

- **Primary path:** Transformers.js loads a Chinese-capable speech model (e.g., MMS-TTS, SpeechT5, or Kokoro-based models with Chinese support) and runs inference on-device via WebGPU/WebNN. The model is downloaded once and cached in the browser (IndexedDB or Cache API). Subsequent poem recitations are instant with no network dependency.
- **Fallback:** Web Speech API (`speechSynthesis`) for browsers that lack WebGPU support. Quality varies by OS/browser, but it's functional and requires zero setup. The app detects WebGPU availability at startup and routes accordingly.
- **UX:** Play button on poem display. Optional auto-play in settings. During Living Scroll mode, audio can play the full poem before the student begins the character reveal, setting the auditory memory before the recall test.
- **Model selection criteria:** Must support Mandarin Chinese with accurate tonal pronunciation. Model size should be under ~100MB for reasonable first-load experience. Quantized (INT8/INT4) models preferred for faster inference and smaller downloads.
- **This is the first real use of the WebGPU/WebNN infrastructure** that justified the Chromium-only constraint. TTS ships before any other AI feature, proving the client-side inference pipeline on a concrete, high-value use case.

**Ear Training — two listening modes (沉浸听诵 + 听诵复习):**

This feature lets students learn and review poems by voice alone, without looking at a screen. It's ideal for car rides, falling asleep, doing chores, walking, or any situation where eyes and hands are occupied. Both modes build on the same Transformers.js TTS engine.

*Passive Listening (沉浸听诵) — no interaction, pure immersion:*

- The app plays through today's due poems as continuous audio, like a playlist
- **SRS-weighted repetition:** Poems are not played equally. The loop weights frequency by SRS stability — poems with low stability (struggling, short review intervals) play 2-3x per cycle, while mastered poems (high stability, long intervals) play once. This creates a spaced-repetition effect through exposure frequency alone, even without explicit ratings
- **Poem structure per play:** Title announced first ("静夜思, 李白"), brief pause (1s), then the full poem read at a measured, recitation-appropriate pace. Between poems, a 3-second silence so the student can mentally echo what they just heard
- **Loop behavior:** After all due poems play once (weighted), the cycle repeats. Configurable in settings: loop N times, loop for N minutes, or loop until stopped
- **Background audio:** Uses the Web Audio API and Media Session API so playback continues when the phone is locked or the browser tab is backgrounded. Lock screen shows "Kuibu — Listening" with poem title, play/pause, and skip controls
- **Wake Lock API:** Prevents the device from sleeping during a listening session
- **No SRS state changes.** Passive listening is exposure, not assessment. Review state is unaffected. The parent analytics dashboard can show "listening time" as a separate metric from "active review"

*Active Listening (听诵复习) — audio-only spaced repetition:*

- Same audio flow as passive mode: title announcement, poem recitation
- After the poem finishes, a distinct soft chime (not jarring — a wooden block knock 木鱼 or a gentle bell, matching the aesthetic) signals "rate your recall now"
- The app waits for a rating via three input channels, whichever comes first:

  **Channel 1 — Voice command (primary for hands-free):**
  Web Speech API `SpeechRecognition` (on-device in Chrome). The active vocabulary is just 4 words, so recognition accuracy is very high. Supported commands:
  - "忘了" or "forgot" → Forgot
  - "困难" or "hard" → Hard
  - "不错" or "good" → Good
  - "简单" or "easy" → Easy
  Continuous listening mode with a 10-second timeout. If no command recognized within 10s, auto-rate as "Good" (configurable default in settings) and move on, so the session never stalls.

  **Channel 2 — Headphone button taps (best for noisy environments):**
  Media Session API maps physical headphone buttons:
  - Single tap → Good (the most common rating, lowest friction)
  - Double tap → Easy
  - Triple tap → Hard
  - Long press → Forgot
  Works with any Bluetooth headphones or wired earbuds with inline controls. More reliable than voice in noisy environments (bus, street, kitchen).

  **Channel 3 — Screen tap (fallback):**
  Minimal lock-screen-style UI with four large, high-contrast tap zones filling the screen. Designed for a quick glance-and-tap without reading. The four zones use the app's color language: a muted tone for Forgot, warm tones graduating to the vermillion accent for Easy.

- After rating: SRS state updates exactly as in the visual review modes (same algorithm, same scheduling). Next poem plays immediately.
- **Session summary:** When all due poems are reviewed (or session is stopped), a brief audio summary: "Today's listening review complete. N poems reviewed." The visual session summary shows the same calm report as visual review sessions.

*Shared infrastructure for both modes:*

- **Playlist generation:** On session start, query all poems where `next_review_at <= now()` for the current student. Order by priority: lowest stability first (these need the most reinforcement). In passive mode, assign repetition weights. In active mode, play each once.
- **Offline capability:** Since TTS runs on-device via Transformers.js, and the poem text is cached locally, ear training works without network once the TTS model is downloaded. Only SRS state sync (active mode ratings) requires network, and these can queue locally and sync when reconnected.
- **Parent controls:** Settings include max listening session duration (default: 30 min), active mode timeout behavior (auto-rate or pause), and whether to include fragments in listening sessions (Chinese fragments only, not English).
- **Analytics:** Parent dashboard shows listening minutes per day, passive vs active split, and for active mode, the same accuracy/retention metrics as visual review.

### Build Sequence (recommended order)

**Phase 1: Core Experience (make a child want to open it)**

1. **Aesthetic foundation + Living Scroll prototype** — Next.js scaffold, Tailwind config, LXGW WenKai font, Xuan paper background, color palette, responsive layout shell. ## Design Decisions (resolved)

1. **Living Scroll = review event.** Scroll completion is an alternative review mode, not separate practice. Completing the scroll triggers the same Forgot/Hard/Good/Easy rating and updates SRS state. This avoids dual accounting complexity and treats the scroll as a more engaging flashcard flip. Students choose their preferred mode (scroll or card flip) per session.

2. **Offline scope: installable PWA, no offline reviews in v1.** PWA provides installable icon, splash screen, and cached static assets. Offline reviews require client-side scheduling and sync reconciliation which conflicts with the Supabase RLS model. V2 can add offline review with optimistic local state and server reconciliation on reconnect.

3. **Hosting pypinyin: batch at build time, API route for custom poems only.** The curated library pinyin is generated once via a Python batch script and stored in the database. Only custom poem creation (paid feature) calls the pypinyin API route at runtime. Fallback: if API fails, allow manual pinyin entry with a "retry auto-generation" button.

4. **FSRS visibility: visible to all, selectable by paid tier only.** Free users see FSRS in the algorithm picker with a lock icon and upgrade prompt. This serves as a natural upsell touchpoint without hiding functionality.

5. **Subscription model: three tiers (Free / Pro / Max), feature mapping flexible.** The `users.plan` field uses an enum that supports FREE, PRO, MAX (and ADMIN). Feature-to-tier gating is enforced in backend middleware via a config map, making it easy to move features between tiers without schema changes. Specific tier assignments for each feature (FSRS algorithm, custom poems, advanced analytics, higher quotas, etc.) will be decided as features ship and usage patterns emerge. Start without payment integration. Manually toggle tiers via Supabase admin. Add Stripe when there are users who want to pay.

6. **Tier config approach:** A single `tierConfig` object maps feature keys to minimum required plan. For example: `{ fsrs: 'PRO', customPoems: 'PRO', advancedAnalytics: 'MAX', maxStudents: { FREE: 2, PRO: 8, MAX: 120 } }`. This config is shared between frontend (UI gating, upgrade prompts) and backend (middleware enforcement). Changing which tier unlocks a feature is a one-line config change, not a code change.
